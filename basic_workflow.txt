================================================================
Workflow: snapshot package integration with simple_trainer
================================================================

GOAL
----
End-to-end exercise of the `snapshot` package against this repo: build a
snapshot from a fresh conda env, push it as an OCI image, then deploy it
into a clean checkout and confirm that subsequent training runs restore
from the snapshot without rebuilding anything. Also: support restoring an
arbitrary user-specified snapshot by tag or id. Finally, verify that
multiple local checkouts of the same git repo can share autosnapshot
generations when their provenance matches, while differing checkout state
selects or creates a different compatible generation.

REPOS
-----
- simple_trainer:  ssh://git@github.com/cjolivier01/simple_trainer
                   cloned to ${HOME}/src/simple_trainer
                   (clone it there if it isn't already present)
- snapshot:        the python package being exercised
                   assumed to live at ${HOME}/src/snapshot
                   (i.e. ../snapshot relative to this repo's root)

PREREQUISITES
-------------
- `mamba` is available on PATH
- ssh access to the github repos above
- A CUDA-capable host (workflow installs cu130 torch wheels)

================================================================
Phase 1 -- Reach the "stable start state"
================================================================
The "stable start state" means: a fresh conda env exists with all deps
installed and snapshot env vars exported, AND the workspace has zero
local snapshot images and zero OCI snapshots in the layout dir.

1. cd ${HOME}/src/simple_trainer

2. Clear any pre-existing local snapshot images for this repo:
     - After cleanup: `snapshot image ls` MUST return zero entries.

3. Create a fresh conda env (random suffix keeps runs isolated):
     mamba create -n snap-$(openssl rand -hex 6)-$(uname -p) python=3.11.6
   Then activate it.

4. Install deps via a single script in scripts/. This script must be
   created in this repo (it does not exist yet):

     scripts/setup_env.sh
       - installed pip packages should go into the conda environment
         site-packages and not ~/.local -- this script should not
         install anything under ~/.local
       - pip install torch torchvision torchaudio \
             --index-url https://download.pytorch.org/whl/cu130
       - pip install -r requirements.txt
       - install the snapshot package (editable from ../snapshot when
         present; otherwise from its git remote)
       - install anything else this workflow relies on (utilities used
         by env.sh, the reset script, or the integration test)

   Goal: a one-shot, reproducible "env is ready" command.

5. Source env.sh from the repo root (create it if missing):

     #!/usr/bin/env bash
     CONDA_ENV_NAME="$(basename ${CONDA_PREFIX})"
     export SNAPSHOT_CACHE_DIR="${CONDA_PREFIX}/snapshot-cache"
     export SNAPSHOT_OCI_LAYOUT_PATH="${CONDA_PREFIX}/snapshot-oci"
     export SNAPSHOT_OCI_TAG="${CONDA_ENV_NAME}"
     mkdir -p "${SNAPSHOT_CACHE_DIR}"
     mkdir -p "${SNAPSHOT_OCI_LAYOUT_PATH}"

   Order: activate conda env first, THEN `source env.sh`, so
   ${CONDA_PREFIX} is set when env.sh runs.

6. Verify the stable start state:
     - `snapshot oci ls`   -> zero entries (new env, empty layout dir)
     - `snapshot image ls` -> zero entries (no local snapshots)

================================================================
Phase 2 -- "Reset to stable start state" script
================================================================
Add scripts/reset_to_start.sh. It must idempotently return the
workspace to the Phase 1 end state, so any later step in this
workflow can be re-run from a clean slate without rebuilding the
conda env.

Behavior:
  - Remove all local snapshot images for this repo.
  - Remove any OCI snapshots under ${SNAPSHOT_OCI_LAYOUT_PATH}.
  - Remove bootstrap_train.py, bootstrap_train.py.manifest.json,
    and any stable-modules artifacts written into the repo by
    previous runs.
  - Leave the conda env and env.sh exports intact.
  - End by asserting `snapshot image ls` and `snapshot oci ls`
    both return zero entries, and the snapshot runtime cache is empty;
    exit non-zero if not.

================================================================
Phase 3 -- Build, tag, and push a snapshot
================================================================
1. First run: `./lenet.sh`
     Expected (current behavior):
       - Creates bootstrap_train.py and stable-modules file(s)
         on successful exit.
       - Does NOT create a snapshot image.
     Verify: `snapshot image ls` -> zero entries.

2. Second run: `./lenet.sh`
     Expected (current behavior):
       - Creates a snapshot image, then runs training steps.
     Verify: `snapshot image ls` -> exactly one untagged snapshot.

3. Tag and push:
     snapshot tag  <snapshot-id> my/train_lenet:${CONDA_ENV_NAME}
     snapshot push my/train_lenet:${CONDA_ENV_NAME}

4. Tear down local copies:
     - Delete the local tag.
     - Delete the local snapshot image.
     - Delete the local snapshot cache.
     Verify: `snapshot image ls` -> zero entries.
     Verify: `snapshot cache ls` -> zero entries.

================================================================
Phase 4 -- Deploy from snapshot into a fresh checkout
================================================================
1. Clone into a separate working directory:
     cd ${HOME}/src
     rm -rf deployment_simple_trainer
     git clone ssh://git@github.com/cjolivier01/simple_trainer \
         deployment_simple_trainer
     cd deployment_simple_trainer

2. Pull the OCI image and hydrate it as the current snapshot for
   this repo:
     snapshot pull my/train_lenet:${CONDA_ENV_NAME}

   Expected behavior of `snapshot pull`:
     - Fetches the OCI image into ${SNAPSHOT_OCI_LAYOUT_PATH}.
     - Because there is no existing autosnapshot for this repo,
       the pulled image becomes the current/active snapshot.

3. Run the trainer:
     ./lenet.sh
   Expected: restores from the hydrated snapshot. No rebuild.

================================================================
Phase 5 -- Subsequent runs must not rebuild
================================================================
lenet.sh forwards the LeNet defaults through xtrain.py, which uses the default
`--xtrain-external-only=1` (see XTRAIN_FLAGS at tools/xtrain.py:42).

Required snapshot-package behavior under external-only=1:
  - When save_stable_modules is invoked with include_non_repo=True
    and only_non_repo=True, it must write ONLY external (non-REPO_ROOT)
    modules into the stable-modules file(s).
  - Therefore re-running ./lenet.sh after the Phase 4 restore
    must also restore from the existing snapshot with no rebuild.

Verify by inspecting the snapshot package source at ../snapshot to
confirm save_stable_modules honors only_non_repo as described.

================================================================
Phase 6 -- Restore an arbitrary snapshot by tag or id
================================================================
A user must be able to ask for a specific snapshot to restore:

     ./lenet.sh --restore=<tag-or-id>
     ./lenet.sh --xt-restore=<tag-or-id>     # forwarded xtrain shorthand alias

Required xtrain.py behavior:
  - Pull the named tag/id if it is not already local.
  - Hydrate it as the active snapshot for this repo.
  - Take the restore path instead of the bootstrap-or-train path.

STATUS: implemented in tools/xtrain.py as the restore xtrain flag.

================================================================
Phase 7 -- Share autosnapshots across same-remote checkouts
================================================================
This phase extends the workflow after the normal build, push, hydrate,
restore, repeat-restore, and explicit-restore paths have passed.

Goal: prove that

  (a) autosnapshot selection is based on compatible snapshot provenance,
      not on a single checkout directory; and
  (b) a fresh checkout whose source state matches an existing sibling
      checkout's `stable_modules.json` capture can ADOPT that capture
      and immediately hit the existing autosnapshot in a SINGLE run --
      no separate seed pass required. Mismatching source state still
      forces the fresh checkout through its own allow-missing bootstrap
      path and build (or look up) its own autosnapshot generation.

1. Clone three additional simple_trainer checkouts from the same remote:

     multi_same_a
     multi_same_b
     multi_differing

   All three checkouts should use the same conda env, env.sh exports,
   SNAPSHOT_CACHE_DIR, and SNAPSHOT_OCI_LAYOUT_PATH.

2. Clear the shared snapshot repo cache for this repo identity so the
   phase starts with no autosnapshot generations for these checkouts.

3. Seed stable modules in multi_same_a only.

   Expected:
     - multi_same_a writes its own checkout-local stable_modules.json
       under the snapshot repo cache;
     - multi_same_b and multi_differing have no stable_modules.json yet
       in their cache slots.

4. Run multi_same_a a second time to publish the base-state autosnapshot.

   Expected:
     - a base-state autosnapshot generation is created;
     - multi_same_a's checkout-local current marker points at that
       generation.

5. Run multi_same_b once. It has no stable_modules.json of its own.

   Expected NEW behavior (sibling adoption):
     - xtrain detects that can_generate_bootstrap is False, then calls
       snapshot.materialize_sibling_stable_modules(REPO_ROOT). The
       routine finds multi_same_a's capture, verifies equivalence
       (same git HEAD, same dirty .py file set, identical SHA-256
       content for every file in that set) and copies the modules +
       import_deps into multi_same_b's slot with repo_root rewritten
       to multi_same_b. env is intentionally NOT carried over.
     - bootstrap generation succeeds on this same run;
     - the runtime selects multi_same_a's published base-state
       generation via the portable provenance digest;
     - output contains:
         * "adopted stable_modules from sibling checkout: ..."
         * "current autosnapshot hit"
     - output does NOT contain "RE-SNAPSHOT REQUIRED";
     - the shared runtime still has exactly one generation;
     - multi_same_b's checkout-local current marker now points at the
       same base-state generation.

6. Change only multi_differing before its first run.

   Use a deterministic local source change that affects bootstrap /
   autosnapshot provenance. It does not need to be committed.

7. Run multi_differing once.

   Expected:
     - sibling adoption is attempted but rejected (multi_differing's
       source state differs from multi_same_a / multi_same_b: same
       HEAD, but different dirty .py content);
     - xtrain falls back to generating a bootstrap with
       --allow-missing-stable-modules;
     - its changed source state does not match the base-state generation;
     - a second autosnapshot generation is created;
     - the shared runtime now has exactly two generations.

8. Apply the same deterministic source change to multi_same_b and run
   it again.

   Expected:
     - multi_same_b's existing bootstrap manifest no longer matches the
       base-state generation, so the runtime falls through to the
       compatible-generation search and selects the changed-state
       generation that multi_differing built;
     - output contains a current autosnapshot hit;
     - output does not contain RE-SNAPSHOT REQUIRED;
     - the shared runtime still has exactly two generations.

The snapshot-package e2e should run this phase by default. It may expose
an opt-out for faster local debugging:

     SNAPSHOT_SIMPLE_TRAINER_MULTI_CHECKOUT_E2E=0

Integration test (lives in the snapshot package, not here)
================================================================
Location:  snapshot/tests/ (e.g. tests/manual/test_simple_trainer_e2e.py)
Marker:    manual / long-running -- NOT collected by default `pytest`.
SUT:       simple_trainer (public repo, fine to clone in CI/dev hosts).

Requirements:
  - Mirror Phases 1-7 end to end against the real `snapshot` CLI/API.
    No mocking of snapshot internals, torch, or git.
  - The multi-checkout phase should run by default, with an environment
    variable opt-out for faster local debugging.
  - Allowed to clone repos and create conda envs under /tmp; must
    clean them up on success.
  - Emit a clear, timestamped, step-by-step log so progress is
    visible during the (slow) run.
  - On successful completion, clean up everything:
      * /tmp clones
      * OCI layout dir created during the test
      * conda env created during the test
      * any tags pushed-and-then-pulled by the test
  - On failure, leave artifacts in place for inspection and say so
    in the test's docstring / final log line.
